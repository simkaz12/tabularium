# Tabularium

Memory is a harness concern, not a database — Tabularium owns the whole path: the read side (grounding a session, per-role, budget-packed), the write side (what is worth saving, and a gate that refuses junk), and the curation policy in between. A Tabularium stores hypomnemata — durable notes of what was decided and why, kept for recall. This glossary fixes the domain language; the generic architecture vocabulary used in the code and ADRs is module / interface / seam / depth.

## Language

**Tabularium**:
The system / the archive as a whole — the Python library, the MCP server, and the store behind them. Tabularium **is** the memory engine, not a consumer of someone else's: imported libraries supply *mechanisms* (transport, provider I/O, vector storage) at seams beneath it; the memory *semantics* — recall ranking/fusion, dedup, decay, eviction, decision records — are Tabularium's own and are never imported. Informal short form in notes/conversation: **tabu** (e.g. "tabu magic" = Tabularium's own spec logic applied to raw input); the full name stays canonical in the interface and docs.
_Avoid_: the memory, the DB, the index; "framework" (it's the engine, not a wrapper)

**hypomnema** (pl. hypomnemata):
One memory entry — a durable note kept for later recall. Internal term: it carries the meaning but never has to be said aloud at the interface.
_Avoid_: memory, record, row (as the domain term)

**Derivability bar**:
The admission test every hypomnema must pass: *would an agent holding the repo and its ordinary tools recover this just by looking?* If yes, it is not memory — it is a restatement, and saving it is bloat that says nothing. Memory is **what matters and cannot be derived by exploring**. The bar cuts across the Fact/Decision split rather than along it: a Decision never passes derivation (code shows what was built, never what was rejected or why), but neither does a `pitfall` — an environment gotcha, a tooling trap, an hour of debugging that left no trace in any repo. What fails the bar is the cheaply-recoverable restatement: "this module has these functions", "the suite has N tests". Enforced as **practice, not engine** — a write-time worth-judgment would need an LLM in the save path, which ADR 0008 forbids; the levers are the `save` tool's description (what agents are told to save), decay/eviction (what stops mattering sinks on its own), and the offline reconciliation judge (retroactive cleanup). *Derived from the un-re-derivability argument, 2026-07-29.*
_Avoid_: relevance/importance (those rank what is already admitted — the bar decides admission), quality bar (not about how well-written it is), curation (that is the push-side Curator's job)

**Fact**:
A hypomnema holding mutable knowledge — true for now, revisable, reinforced by recall, and decayed out if it goes unused. Time-decay is correct for a Fact. Subject to the **Derivability bar** like every hypomnema: a Fact earns its place by being un-recoverable by exploration (an environment gotcha, a tooling trap), never by restating what the code already shows.
_Avoid_: note, item

**Decision**:
A hypomnema recording what was chosen and why. Its content is immutable — never edited in place. Change is recorded by superseding it, not editing it. Time-decay is *wrong* for a Decision (age ≠ staleness).
_Avoid_: choice; ADR (an ADR is one *rendering* of a Decision, not the Decision itself)

**Supersession**:
Replacing a hypomnema with a newer one that references the one it replaces. The superseded record leaves active recall but stays permanently in the archive, queryable as history. **Both arms**, not Decisions alone — a Fact whose claim has been overtaken is superseded by the Fact that overtook it, which is strictly more informative than flagging it `invalid` and leaving the reader to find the replacement. The two arms differ in *what* supersession asserts, not in whether it applies: superseding a Decision says *we chose differently*, superseding a Fact says *the world moved*. Neither is an edit — content is never rewritten in place on either arm.
_Avoid_: overwrite, update, replace; "invalidation" (a superseded record is usually also invalid, but **Validity** is a bare truth-flag with no successor — supersession is the case where the successor is known and named)

**Revocation**:
Retiring a Decision with no replacement — it stops being in force. Like supersession, it removes the Decision from active recall without deleting it.
_Avoid_: delete, remove

**Evergreen / Dated decision**:
Evergreen = a Decision still in force however old (never superseded or revoked). Dated = one that has stopped applying. The distinction *emerges* from supersession + reference frequency — it is never a flag set at write time.
_Avoid_: permanent/temporary, active/expired

**Hot**:
A Fact lifecycle state: the capped, contended session-start attention tier — the small set (a few slots per scope) surfaced automatically at session start. Membership is *earned* by importance and *persisted* (a stored state, not a read-time recompute); when the tier is full, an LLM-judge evicts the loser. Tabularium collapses project-b's separate `pinned` kind + `is_hot` flag into this one state — importance-promotion needs no discrete kind, and keeper-status is emergent from reference frequency (per ADR 0001), never a write-time "keep forever" flag.
_Avoid_: pinned (rejected as a separate state), is_hot (project-b's conflated flag), "hot" in the storage/database sense (a high-traffic table, a hot path, a hot cache) — Hot names a *lean, capped, mission-critical* attention tier, so borrowing the word for "whatever gets written most" inverts its meaning; say **high-traffic table** or **write-dominant path** instead

**Ember**:
A Fact lifecycle state: a hypomnema born *hot* at write-time — a transient, self-decaying, directional nudge; a warm coal kept in the pocket that keeps pointing the right way. Defined by its **attention profile** (born warm → fades if unreferenced → escalates if it recurs), *not* by valence. An ember is **valence-neutral**: it may be a *correction* (negative — "you added inline comments; the guidelines forbid it") or a *guideline / pointer* (neutral — "prefer the new API while we refactor"). Valence lives on `source`, orthogonal to ember-ness; the eval harness consumes only the *correction*-valence subset as a labeled failure corpus. A recurring ember escalates up a ladder — session-start nudge → codified Decision (a "hard rule" or convention), suggested not automatic.
_Avoid_: pin (an ember is *transient* — it decays; a permanent pin was rejected), warning/error (valence-neutral), reminder

**Validity**:
A truth-state carried by every hypomnema (Fact *and* Decision), orthogonal to its lifecycle: `valid` (holds in the world) vs `invalid` (no longer holds / turned out false). A mutable, *bidirectional* toggle — the environment can change truth either way. Invalidating never removes data: a wrong-but-meaningful record is kept as history and eval signal. Distinct from lifecycle ("is it in active recall / how much attention") — e.g. a Decision can be `in_force` yet `invalid` ("still nominally in force, but its premise turned out false").
_Avoid_: true/false as a content edit (validity is metadata *about* the frozen content, never an edit of it), stale/expired

**Burial**:
The strongest removal in Tabularium — retiring a *truly-useless* entry (a slip, mis-save, or hallucination carrying no signal) from the active store while **always leaving a tombstone**. Burying drops the content **and every derived index of it** (vector, FTS row) — complete because content lives in exactly one place (the event log, pair registry, and counters carry ids, never content; T04). One stated exception: content quoted in a descendant Decision's birth-frozen lineage survives — that quote is the descendant's identity fact; if it must truly go, bury the quoting record too. There is **no true hard-delete**: even garbage leaves a marker, so the archive is *monotonic* (nothing is ever fully forgotten). Explicit and rare; available on both arms; never automated. Distinct from *invalidation* (keeps the whole record, marked false) and *archival* (a reversible decay exit that keeps the Fact whole).
_Avoid_: prune, delete, purge (all imply total erasure — burial always leaves a tombstone)

**Tombstone**:
The lightweight marker a burial leaves behind — id, type, reason, timestamp, and whether the entry was model-generated — retained so the eval harness can count burials as (usually) model slip-ups even though the buried content is gone. The mechanism that keeps the archive monotonic.
_Avoid_: audit-log entry (a tombstone is a first-class retained record, not a side log)

**Bounce**:
The dedup gate's refusal to write — a near-neighbour sat above its arm's gray floor, so nothing was saved and the caller must adjudicate. Not an error: the gate working. The envelope reports **evidence only** — the candidate, its similarity, which guard tripped, and a `verdict` naming what was observed (`near_dup`, `guard_trip`, `decision_adjacent`) — and never a conclusion, because similarity measures topic adjacency and cannot see intent: a restatement, an elaboration, a sequencing note and a genuine supersession all produce the same high cosine. Two shapes, split on the kind being **saved** (never on the candidate's kind — that split offers exits the caller cannot execute). *Sharpened 2026-08-06; see ADR 0022.*
_Avoid_: rejection, failure, duplicate-detected (all read as an error); "the gate blocked it" (it declined and handed back a judgement)

**Exit**:
A named, executable way out of a bounce or an ember escalation — a pair of an exact call (`how`) and the content judgement that selects it (`when`). **The engine names the exits and chooses none**: which one fits is a judgement about meaning that no threshold or count can answer. Established by the ember ladder (SPEC §8.4) and extended to the dedup gate. Declining every exit is always available and needs no exit of its own.
_Avoid_: suggestion, recommendation, suggested action (each asserts a conclusion the engine has no evidence for); option (too weak — an exit carries the literal call)

**Recall**:
Query-driven hybrid retrieval — the headline §4 differentiator. Takes a query + scope, fans out two raw legs through the storage seam (`vector_search` + `text_search`) **in parallel**, fuses them above the seam (RRF), and returns ranked hits. A memory *semantic* Tabularium owns, never imported (ADR 0005). Its consumers: the topic-shift path of the session interface, and the pairwise probe T07's dedup reuses. **A distinct module from Context composition** — query-in / ranked-hits-out.
_Avoid_: search, query (too generic); "two-stage" (the legs run in parallel, not as a narrowing pipeline — R05 §4)

**Context composition**:
The **query-less**, token-budgeted assembly of the session-start payload — the small set of highest-attention entries (`hot` Facts, embers) packed into a token budget and surfaced automatically when a session opens. Decisions are pull-only at session start (M2 slice C task 12, 2026-08-01) — reachable via `decisions_query` / `decision`, never a payload tier. **A distinct module from Recall** — budget-in / packed-payload-out, no query — though it may *call* Recall for a topic-shift sub-case. project-b's `GroundingService` / `HotContextPayload`.
_Avoid_: recall (that is the query-driven sibling); grounding (project-b's name — the module is Context composition)

**Session**:
One entry in the **Sessions** module — an append-only summary of a single digest episode, carrying a `scope`, a server-derived time range, and a prose body, and nothing else. **Not a hypomnema**: never embedded, never deduped, never decayed, no lifecycle and no validity — which is precisely why it is a separate module and not a fourth `kind`, since `kind` is the discriminator for embedding-driven machinery and an unembedded kind would consist of nothing but opting out of what kind means. Queried two ways and only two: by **time range**, and by **BM25 over the body**. A row's range is a *contiguous, non-overlapping partition of time per scope* — `ended_at` is the write moment, `started_at` is the previous row's `ended_at` — so the relation to hypomnemata is **computed, never stored**: the atoms a Session produced are those in its scope whose `created_at` falls inside its range. A row is one *episode*, not a whole conversation: the digest cadence is per-task, so one conversation normally writes several. External identifiers (a Jira key) ride inside the prose where BM25 finds them, never in a typed field — that structure is meaningful in one scope and empty in the rest, so it never earned a column.
_Avoid_: hypomnema (a Session is not one — no embedding, no lifecycle, no validity); context / Context composition (that is the push-side session-start packer, and a live tool already owns the name); digest (names the act of writing one, not the record); log entry / journal (implies an append-only side-channel rather than a first-class queryable record)

**Decision-record view**:
The engine-produced markdown rendering of one Decision — a **metadata frame** (status line, backward supersession history + one-hop forward pointer, `promoted_from` snapshots) around the **verbatim immutable content**. **Byte-stable**: the rendered resource changes *iff* the decision has its own semantic transition — the render is a pure function of the decision's own row (all lineage birth-frozen; a chain grows only at the tip), and live reference stats live only in the model-facing views (`DecisionView`, `decisions_query`), never in the resource. The frame is column-derived truth; the body is the decision as spoken — never parsed or restructured ("an ADR is one *rendering* of a Decision"). Title derived (first sentence, truncated), never a stored field. Provenance is *not* its job: credibility against back-dating comes from the dogfooding practice (T10 — decision artifacts committed to the repo as they land), not from engine machinery.
_Avoid_: parser, template (the view frames, it doesn't impose structure); report/export (it is addressable live state — `decision://{id}` — not a batch artifact)

**Lineage**:
A Decision's birth-frozen identity facts about where it came from: its supersession chain (`{id, title, created_at}` snapshots of *every* predecessor, captured at birth) and its `promoted_from` snapshots (the embers that justified it, captured *as they stood* at promotion). **Captured at birth and frozen** — lineage is part of the decision's identity, like `created_at`; later changes to the source records (an ember fading, an ancestor being buried) never rewrite it. The forward direction (`superseded_by`) is set exactly once, at the decision's own supersession. No chain "group" entity exists — each decision carries its own backward history, so the rendered record is a pure function of its own row; chain identity, if ever needed, is the root's id.
_Avoid_: history (ambiguous with reference stats), thread, group (implies a stored entity)

**Sync**:
The idempotent export CLI — `tabularium sync <path>` — that loops every Decision and writes its byte-stable T09 render to a file under `docs/decisions/`. Safely re-runnable; after-run `git status` shows exactly the semantic transitions since the last sync (C superseding B produces two file changes, nothing more). The CLI imports `tabularium` engine directly — it is the "dogfood-from-code imports the library" consumer ADR 0012 B0 promised, and the library seam's standing proof. Never an engine behavior; the commit that follows is human.
_Avoid_: export job (implies batch/scheduled behavior, not a deliberate CLI call); auto-commit (git never enters the engine)

**Scope**:
The isolation namespace on every hypomnema — a flat validated *name* (`tabularium`, `project-a`, …; pattern `^[a-z][a-z0-9-]{0,31}$`, `global` reserved, never normalized), `scope: str` on the wire (ADR 0012 B7). One reserved name, **`global`**, is the owner-wide tier; every other name is a peer named scope. A scope names a **working context** (a product/effort), never a repo — a cross-stack pair (project-a-api + project-a-web) shares one scope; the repo→scope binding lives in each repo's client config, and the engine never knows what a repo is. Exactly two tiers, one engine-owned semantic: **a read in scope X sees X + `global`** (recall, decisions_query, context composition alike; hits labeled with their origin scope; reading `global` sees global alone); **a write targets exactly one scope** (`global` is an ordinary, explicitly-addressable write target). The dedup gate probes what recall sees — a save into X probes X + `global`; sibling scopes never probe each other. Hot tiers are per-scope arenas; composition merges the X + `global` pool by rank with no scope quotas. Never nested — no hierarchy, no paths; finer partitioning is T12's facets, not scope structure. A **registered vocabulary**: declared once via CLI (`tabularium scope add` — a human act; agents consume scopes, never create them; `global` pre-registered); an unregistered name on any model-facing call is a `ToolError`, so a typo cannot fork a ghost namespace.
_Avoid_: scope_kind/scope_id (project-b's struct — a two-value kind with a vestigial id), per-repo scope (the product is the unit, not the repo — project-b's split of the project-a pair is the counterexample), namespace path/hierarchy (rejected), audience (that's T12's axis), "user scope" (the owner-wide tier is `global`; no users exist)

**Owner**:
Not a domain concept. One Tabularium deployment = one store directory = one human's archive — the embedded-database idiom (the store directory is the tenant boundary, the way a SQLite file is). No user table, no owner column, no principal argument anywhere; identity is configuration (which store you open), never a query. Multi-owner = a second store. If multi-owner ever came, owner attaches as a facet of the scope key — one type widens, zero tool signatures move. Agents (Claude Code, Agent-X) are *not* owners — they are agents of the same owner sharing one archive; agent identity rides `source`.
_Avoid_: user/tenant (no such rows exist), owner resolver (project-b's guessing bug — nothing to resolve)

**Purpose (facet)**:
An optional, single-valued facet on any hypomnema (both arms) naming its **intrinsic utterance type** — what the writer knowably said, never who it's for and never where it's delivered. A registered vocabulary (CLI-declared like scopes; an unregistered value on save → `ToolError`), five values pre-registered: `constraint` (hard guardrail — violating = incident), `convention` (house style — violating = bad work), `preference` (owner taste), `pitfall` (known trap — where you'll trip next time), `reference` (pointer to an external resource). `None` is the honest default — most real saves are plain working state fitting no value (75% in the 2026-07-22 live-project-b sample); a value ships only while a default delivery-policy row consumes it. `finding` (empirical discovery — what was true when you looked) is the first documented candidate registrant, deliberately unregistered until a policy row wants it.
_Avoid_: tag/category (folksonomy — this is a registered vocabulary), grounding (a delivery outcome, not an utterance type — killed), rationale (that's `kind=decision`), warning (reserved away from valence-neutral embers — the durable trap is a *pitfall*)

**Audience hint**:
The saving model's optional who-needs-this opinion (`audience_hint`, a list of consumer roles, default none) — advisory and **additive-only**. In push composition it can add the entry to a hinted role's candidate pool and boost its rank; it can **never exclude** — not a filter, and pull (Recall) never reads it. Policy (purpose facets → roles) stays the primary router; the hint records the write-time exception policy can't express, valuable because the saving model holds working context no later policy evaluation sees. A stale hint just stops matching — nothing ever goes dark. The additive-only shape mirrors feedback's `[0,1]` range: no backdoor ACL, as feedback has no backdoor eviction.
_Avoid_: audience/ACL (never load-bearing, never hides anything), label (project-b's conflated column)

**Curator**:
The selection module of the push side — `curate(scope, role) → CuratedSelection` — query-less, **token-blind**, push-only. Decides *what deserves attention and in what order* for a given consumer role: applies the delivery profile's facet rules, honors audience hints (additive pool + boost), orders tiers and entries; emits ordered tiers with budget shares. Deliberately separate from Context composition (which packs the selection into the token budget — *what fits*): curation is the precise-tinkering surface, so every tunable concentrates here and the eval harness sweeps it directly, profile-swapping like it swaps fusion strategies. Never touches pull — Recall reads no profiles, no hints.
_Avoid_: composer/packer (that's Context composition), router (nothing is hidden — the Curator allocates attention, not access), per-consumer adapter (policy varies as data, not code)

**Delivery profile**:
The declarative policy object the Curator consumes, keyed by Role: facet rules per tier, tier order, per-tier sort keys, budget shares, hint handling. Data, not code — lives in store-level config, human-edited, versioned with the store; adding a consumer = writing a profile, zero code. The `default` profile reproduces ADR 0007/0012 behavior verbatim.
_Avoid_: adapter (a profile is data at the Curator's seam), ACL/visibility rules (profiles allocate push attention only)

**Role**:
A registered consumer identity naming a **working function** (`implementer`, `investigator`, `scout`), never an agent product or model — the agent→role binding lives in client config, the way repo→scope does. One vocabulary shared by delivery profiles and audience hints; third registry under the one house contract (scopes / facets / roles: CLI-declared human act, unregistered anywhere → `ToolError`, one reserved member each). `default` is reserved + pre-registered: the profile used when `role` is omitted — the main session never claims anything. Cooperative self-identification, never authentication: no principal exists (no owner), and nothing is hidden, so a false claim gains nothing.
_Avoid_: audience (project-b's conflated column), agent/persona (brand names — the registry outlives the roster), user (no users exist)

**Cleaner**:
The **periodic** judged-curation module — the trash-clearing half of the push side, and the replacement for the parked decay-by-disuse (2026-08-07). An **engine module**, not a harness script: the harness contributes only the trigger. Judges on **two axes**: *relevance* (does this still deserve to be in the store) and *falsity* (has it stopped being true). The two axes are judged differently because the properties differ in kind — relevance is **intrinsic** to a record's text (the admission questions are answerable blind, with no tools), while falsity is **extrinsic** and cannot be read off a record at all, so the falsity axis runs as a **pair-contradiction sweep**: retrieval surfaces a newer record contradicting an older one and the panel adjudicates the *pair*, never a lone record — which makes falsity intrinsic again and preserves the blind, parallel, batched **Judge panel** shape. Its verdict vocabulary is exactly two writes, both reversible: **Shelving** on the relevance axis, **Supersession** on the falsity axis. It **never buries** — Burial stays owner-only — and it never writes to the `global` scope, which stays owner-curated; a contradicted `global` record is detected and surfaced, never acted on. Distinct from the **Curator**, which allocates attention among records that are staying; the Cleaner decides which stop being in the working set at all.
_Avoid_: decay/eviction (the mechanism it replaced — the Cleaner judges, it does not age things out), garbage collector / pruner (imply deletion; the Cleaner's verdicts are reversible dispositions), Curator (the sibling module — attention allocation, not removal), reconciliation judge (the specced-but-absent offline dedup module; a different job)

**Watermark**:
The Cleaner's per-scope bookmark — a `created_at` position marking what a pass has already judged. Each pass judges the records born since the last **completed and verified** pass, which makes the Cleaner a *tail* pass over new arrivals rather than a sweep over the store, and makes batch size **emergent rather than chosen**: a batch is whatever was written since last time. Fits both axes, because the pair-contradiction sweep is already driven by the newcomer as probe. Chosen over a per-record review marker (no such field exists, and `updated_at` cannot stand in — a record examined and *kept* is indistinguishable from one never seen). Skipping is harmless: the next pass simply judges a larger batch, so nothing is lost, only deferred.
_Avoid_: cursor/offset (implies pagination through a fixed set), `reviewed_at` (the rejected per-record alternative), high-water mark (the storage idiom, about durability rather than review)

**Judge panel**:
The two **independent, blind** LLM judges the Cleaner runs over a batch — deliberately **cross-model** (a Sonnet and a GPT, not two runs of one model), given no tools and no MCP, scoring only the batch text against a rubric that restates the **Derivability bar** as yes/no questions. Output is an ordered categorical grade with **no neutral middle** (`shelve-clear / shelve-lean / keep-lean / keep-clear`) plus a capped `unclear` escape hatch and a mandatory per-record `why` — never a numeric score, never free text. Every rubric carries a pool-measured **expected-distribution anchor**, because judges inflate without a scarcity frame.
_Avoid_: ensemble/voting (two judges do not vote — the bands are named and handled differently), grader/scorer (the output is a verdict, not a score), reviewer (that is the human)

**Split band**:
The records a **Judge panel** disagreed on — one judge says remove, the other says keep. Its counterpart bands are *unanimous* (both say remove) and *untouched* (both say keep). Named as a band because it is handled by policy, not per-record: in a **reversible** pass the more-aggressive judge is applied (a wrong shelve costs one undo; a missed one costs permanent noise), and a heavy skew toward one judge tells you which judge is looser, never that the looser judge is wrong — so skew is not grounds to abstain.
_Avoid_: disagreement/conflict (too generic), gray band (that is the dedup gate's similarity region — a different mechanism entirely), tie (there is no neutral middle to tie on)
