# 0020 — The hot tier is owner-curated, not earned

> **Frozen 2026-08-07.** Historical prior — it records what was decided and why at the time, is
> not maintained, and diverges from the built system in places. There is no present-truth
> document: the code is what is true now, and new architectural decisions are recorded in the
> Tabularium store, not as new ADR files. `README.md` orients.

**Status:** accepted — **amends** [0006](0006-fact-taxonomy-validity-and-monotonic-dispositions.md) (supersedes only its "`hot` is earned" clause and the `hot_promote_threshold`/`hot_demote_threshold`-driven contest it implies; everything else in ADR 0006 stands — see Consequences).

`hot` is always-on: every hot record is injected into every session-start payload (SPEC §7's `context` composition). ADR 0006 designed `hot` as "earned only" — importance crosses a promotion floor, wins a slot in a capped per-scope contest, and is evicted by the lowest-importance loser when full, with hysteresis to prevent flapping (SPEC §8.5). That contest was built the same day as this ADR, as a pure synchronous function (`engine/lifecycle.py::sweep_hot`) plus an in-process scheduler, and both passed review before either landed in a commit or reached a deployment.

They were ripped out anyway, on the owner's call, before either shipped: an importance heuristic filling an always-on, fixed-token-budget tier does not average out to a healthy working set — it converges toward permanent occupancy. The contest's own hysteresis (needed to stop legitimate flapping) makes this worse, not better: once a Fact clears the promotion floor and wins a slot, only a *strictly higher* candidate or a fall below the (lower) demotion floor ever displaces it. Nothing in the design ever asks "does this still deserve to occupy every session's fixed budget, forever" — it only asks "is anything else more important right now." At the operating volume this system runs at (~110 saves/week), that question resolves to "no" for a very long time once a handful of Facts clear the bar, and the tier is exactly the wrong place for that outcome, because it is the one tier every session pays for whether it is used or not.

The conflict was not discovered mid-build — it was already in the record. The owner had stated the governing rule twice before this task: session-start memory injection must be a *curated* hot set, never the whole ledger, and a preference for a curated id allowlist for hot-or-not triage over an automatic one. The sweep design satisfied ADR 0006's letter while violating that standing constraint.

## Decision

Hot membership is an owner action, not a computed outcome. One tool, `set_hot(id: HypomnemaId, hot: bool) -> Hypomnema`, joins `set_validity` / `bury` / `revoke` in the disposition family — the same family ADR 0001's automation invariant already reserves for burial and Fact→Decision codification, both explicit owner acts, never automation. `set_hot` is Facts-only (a Decision id is a `ToolError`) and is the *only* `{active, ember} → hot` edge **[the `ember` case is a same-day amendment — see the last Consequences bullet below]**; there is no sweep, no scheduler, and no other code path that ever writes `lifecycle="hot"`.

`set_hot(id, hot=False)` is the deliberate, tool-driven `hot → active` edge — the mirror of promotion, same tool, reversed. Both directions are Facts-only and both are idempotent re-ops in their own direction (an already-`hot` Fact promoted again, or an already-`active` Fact demoted again, is a no-op, no adapter write).

**Automatic demotion survives, but only as housekeeping — a structural consequence, never a policy re-judging the pin.** A hot Fact that is buried, invalidated, or (once M3 decay ships) archived stops being presented in the hot tier:

- **Bury** drops the record entirely — nothing to demote, it simply cannot be selected.
- **Invalidate** (`set_validity(valid=False)`) never touches `lifecycle` at all — the record stays `lifecycle="hot"` in storage, and leaves the *presented* tier purely because `select_default`'s existing valid-only filter excludes invalid records from every tier, hot included. The owner's pin is not overridden; the record is just no longer a valid live Fact.
- **Archive** (once decay ships) will use the same `lifecycle` field the promotion edge uses — a Fact reading `lifecycle="archived"` cannot simultaneously read `lifecycle="hot"`, so there is nothing for a second mechanism to reconcile.

None of these three paths needed new code to get this right: `select_default`'s existing filters and the single-valued `lifecycle` field already make it true. This is the thing worth naming — the housekeeping fell out of the existing design once the sweep was removed, rather than needing a replacement sweep of its own.

`hot_cap` (SPEC §8.5's seed, 5/scope) survives, but its job changes from *contest ceiling* to *payload-size guardrail enforced by rejection*: `set_hot(id, hot=True)` past the cap for the Fact's scope raises `ToolError` naming every Fact currently hot in that scope, so the owner — not the engine — decides what leaves before promoting another. It never silently evicts the lowest-ranked occupant; a curated pin disappearing on its own is exactly the class of surprise this ADR exists to remove, and eviction-on-cap would just be the withdrawn sweep's eviction half wearing a different name.

`hot_promote_threshold` and `hot_demote_threshold` (the contest's promotion floor and hysteresis dead-band) are now dead config: no code path reads them. They are left in place rather than deleted — removing a config field is a larger diff than this decision needs, and an unread field costs nothing sitting inert, the same treatment `hot_rejection_count` already had on the Fact model before this ADR (defined, never incremented).

## Considered options

- **Keep the sweep, narrow the promotion floor.** Rejected: raising the bar delays the convergence, it does not change its direction — any importance-only filter on an unbounded-duration, always-injected tier eventually fills and stays full.
- **Hybrid: sweep proposes, owner confirms.** Rejected as unneeded complexity for this slice. The owner already curates by hand at the volume this system runs at, and a proposal queue is a second surface with no consumer yet — it can be revisited if hand-curation ever stops scaling.
- **Delete the withdrawn sweep design outright, no record.** Rejected. It is kept, as built, in the project history — a real design that passed its own gate and lost anyway is worth being able to read again, not memory-holed.
- **Chosen:** owner-curated promotion via `set_hot`, structural (not mechanism-added) housekeeping demotion, `hot_cap` as a rejection guardrail.

## Consequences

- Supersedes ADR 0006's "`hot` ... **Earned only** (importance + winning a slot; LLM-judge eviction when the tier is full) — never born-into" clause (ADR 0006, "FactLifecycle state machine" section, `hot` bullet) and the trigger/threshold deferral that pointed at this contest. Everything else in ADR 0006 stands unamended: `hot` remains **persisted** (a `set_hot` call must stick, not be re-derived per read — that requirement doesn't change, only who decides the value); `hot`/project-b's `pinned` kind/`is_hot` flag still collapse into the one `hot` lifecycle state (now an *explicit* owner write instead of an *emergent* importance outcome, but still one state, not a second flag); `ember` remains a distinct, write-time-seeded, self-decaying state — birth and fade are untouched by this decision, but promotion is not: **[Amended same day — see the last Consequences bullet below]** an ember CAN be promoted to hot via `set_hot`, as of §8.4 rung 2's Foreground exit.
- SPEC §1.2 and §8.5/§8.6 amended in the same diff as this ADR.
- `set_hot` added to the §9.1 tool surface (11 tools total, up from 10).
- Feeds M3 decay: when `{active,ember}→archived` ships, it inherits the housekeeping contract for free — a hot Fact that decays to archived leaves the tier because `lifecycle` says so, not because decay's implementation needs to know anything about `hot`.
- **[Amended 2026-07-31 — §8.4 rung 2's Foreground exit.]** `set_hot(id, hot=True)` now also accepts a Fact in `ember` lifecycle (previously `active`-only) — the ember ladder's second exit, alongside codification-by-creation. This does **not** reintroduce the earned-promotion path this ADR rejects: the trigger is still a single owner act (a `set_hot` call), never a computed sweep; the owner-asserted recurrence count that motivates the suggestion (`r_owner ≥ escalation_threshold`) is informational only — `set_hot` itself enforces no threshold and will promote an ember at `r_owner=0` exactly as readily as one at the seed. `set_hot(id, hot=False)` demotes to `active`, never back to `ember` (a record that has been through the ladder is no longer provisional), and records a fresh baseline on the Fact's recurrence counters so a later crossing can re-arm rather than re-firing off the frozen standing count. SPEC §1.2/§8.4/§8.5 amended in the same diff as this ADR entry.
- **[Amended 2026-08-02 — per-role grounding, ADR [0016](0016-curation-audience-routing.md)'s amendment.]** `set_hot` gained an optional `roles: list[str] | None = None` parameter that persists a Fact's `audience_hint` (the push-tier routing key) in the same `transition` call that writes `lifecycle="hot"`. This ADR's marquee invariant is intact, not reopened: **`_set_hot` remains the sole writer of `lifecycle="hot"` anywhere in the codebase** — the role tag rides *with* the pin, in this same function, rather than creating a second curation path. Persisting the hint elsewhere (a standalone "set audience" tool, or letting `save`/`ember` mutate an existing record's hint) was rejected for exactly the reason this ADR exists: a second write path for a fixed-budget, always-on tier's contents is the config-map/second-curation-path problem in new dress. `tests/test_hot.py::TestNoAutoPromotion` — this ADR's grep-checkable pin — is unchanged and still green.
